# Linux IoT Gateway

物联网边缘网关：**CC2530 ZigBee 节点 → 协调器 → 串口 → 网关（解析 + 加工 + 落库 + 告警）→ 网页**。

跑在 Ubuntu 上，全 C（POSIX + SQLite），是"嵌入式 Linux 应用开发"岗位的主力项目。

当前进度：**M5-1**（M4 全部保留，新增网页远程控制继电器：按钮 → `/api/cmd` → MQTT → ESP32 → 协调器 → 终端）。
M5-1 里踩到一个真问题：协调器原来用 ZigBee **广播**下发命令，广播在 MAC 层不回 ACK、
丢了不会重发，实测 20 次命令只成 5 次（25%）；改成单播 + `AF_ACK_REQUEST` +
隔 200ms 补发 5 次后解决。
低功耗（节点端）待做；掉线续传决定不做，原因见第 10 节。

## 1. 数据流

```
 CC2530 终端节点            协调器                  Ubuntu 网关
┌──────────────────┐   ┌──────────────┐   ┌──────────────────────────────────┐
│ DHT11  光敏      │   │              │   │ gw_serial  串口(115200 8N1)      │
│ MQ-2   人体红外  │   │  SerialApp   │   │      ↓                           │
│ 继电器  S1       │   │  收到无线帧   │   │ gw_frame   解析 st: 24B           │
└────────┬─────────┘   │      ↓       │   │      ↓                           │
         │ ZigBee 2.4G │  UART0 透传   │   │ gw_filter  中值滤波 + 自适应基线  │
         └────────────►│ 24 字节原样   ├──►│      ↓                           │
                       └──────────────┘   │ gw_alarm   状态机 + 迟滞          │
                                          │      ↓                           │
                                          │  ┌───┴────┐                      │
                                          │  ↓        ↓                      │
                                          │ gw_latest  gw_db                 │
                                          │ (内存快照) (SQLite WAL)          │
                                          │  ↓        ↓                      │
                                          │ /api/latest  /api/history        │
                                          │ /api/stats   /api/alarms         │
                                          │  └────┬───────┘                  │
                                          │   http_srv (内置 HTTP, epoll)     │
                                          │      ↓                           │
                                          │   浏览器 / 手机                   │
                                          └──────────────────────────────────┘
```

网关不重新组包、不改写原始数据，只做"收 → 解 → 加工 → 存 → 给人看"，
保证任何一环出问题都能用原始字节回溯（`env_data.raw` 留着原始 24 字节）。

## 3. 帧协议（st: 固定 24 字节）

这就是 CC2530 固件里 `EnvMsg` 结构体的原样字节流，小端。

| 偏移 | 长度 | 字段 | 取值 / 说明 |
|---|---|---|---|
| 0 | 3 | `'s' 't' ':'` | `0x73 0x74 0x3A` 帧头 |
| 3 | 1 | `'e'` | 帧类型 = 环境数据 `0x65` |
| 4 | 1 | `temp_dec` | 温度小数位 0~9 |
| 5 | 1 | `temp_int` | 温度整数位 → **T = temp_int + temp_dec/10** |
| 6 | 1 | `hum_dec` | 湿度小数位 0~9 |
| 7 | 1 | `hum_int` | 湿度整数位 → **H = hum_int + hum_dec/10** |
| 8 | 1 | `node` | 节点号 1~255（0 视为非法） |
| 9 | 3 | `x` `y` `z` | 三轴，固件未接，恒 0 |
| 12 | 2 | `pir` | 人体红外：0=无人 1=有人 |
| 14 | 2 | `lux` | 光照 ADC 0~1023（**越大越亮**） |
| 16 | 2 | `rsv2` | 备用，恒 0 |
| 18 | 2 | `gas` | MQ-2 烟雾 ADC 0~1023 |
| 20 | 2 | `relay` | 继电器状态（借用 `rsv3`）：0=OFF 1=ON |
| 22 | 2 | `adc` | 未使用，恒 0 |

真实样例（21.1℃ / 51.0% / 858 lux / gas 26 / 无人 / 继电器 OFF）：

```
73 74 3A 65 01 15 00 33 01 00 00 00 00 00 5A 03 00 00 1A 00 00 00 00 00
└─ st: ─┘ └e┘ T1.5 H0.3 n1  x y z   PIR  └lux┘ rsv2 └gas┘ rly  adc
```

### 为什么没有 CRC，怎么保证不出错

这个协议**没有长度字段、没有 CRC、没有序号**，是固件原样吐出来的。校验只靠字段合法性：

1. **4 字节帧头**全匹配（含类型字节），误判率约 1/2³²；
2. 温度 `dec ≤ 9 且 int ≤ 60`、湿度 `dec ≤ 9 且 int ≤ 100`；
3. **`node ≠ 0`**（固件从 1 开始分配）；
4. `pir ∈ {0,1}`、`relay ∈ {0,1}`、`lux ≤ 1023`、`gas ≤ 1023`（10 位 ADC）。

这些条件合起来等效于一个很弱的校验：串口只要错 1 个字节，后面所有 16 位字段都会左移一位、高位变成非 0 从而超范围，实测能被拦住（见单元测试用例 4/5）。

**代价是只能检错、不能纠错**：校验不过就丢掉这一帧、滑到下一个帧头，绝不会把坏数据写进数据库。真要更强保护，得在固件里给 `EnvMsg` 加 CRC16——那是后续可选优化。

## 4. 数据库

```sql
CREATE TABLE env_data (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  ts       INTEGER NOT NULL,   -- Unix 秒（wall clock）
  node     INTEGER NOT NULL,   -- 节点号
  temp_x10 INTEGER NOT NULL,   -- 温度 x10：21.1℃ → 211
  hum_x10  INTEGER NOT NULL,   -- 湿度 x10：51.0% → 510
  lux      INTEGER NOT NULL,   -- 0~1023
  gas      INTEGER NOT NULL,   -- 0~1023
  pir      INTEGER NOT NULL,   -- 0/1
  relay    INTEGER NOT NULL,   -- 0/1
  raw      BLOB                -- 原始 24 字节，排障用
);
CREATE INDEX idx_env_ts      ON env_data(ts);
CREATE INDEX idx_env_node_ts ON env_data(node, ts);

-- M4：告警是「事件」，不是「采样」，所以单独一张表
CREATE TABLE alarm (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  node     INTEGER NOT NULL,
  start_ts INTEGER NOT NULL,   -- 告警开始
  end_ts   INTEGER,            -- NULL = 还在告警中
  base_gas INTEGER,            -- 触发时的基线
  trig_gas INTEGER,            -- 触发那一帧的 gas
  peak_gas INTEGER             -- 期间最高
);
CREATE INDEX idx_alarm_start ON alarm(start_ts);
```

设计取舍：

- **温湿度存定点整数（x10）而不是 REAL**：避免 `21.1` 存成 `21.099999`，查询和绘图都干净。
- **存 raw 原始字节**：现场数据不可复现，出问题必须能追到串口上到底收到了什么。
- **`synchronous=NORMAL` + WAL**：环境数据 1 秒 1 条，掉电丢最后几条无所谓，换来约 10 倍写入速度；但绝不用 `MEMORY`（整库都可能丢）。
- **批量提交（默认 20 条）**：每条 autocommit 都要一次 WAL 提交，攒一批摊薄开销。
- **告警单独建表，不塞进 `env_data` 当一列**：一次告警横跨几十秒、几百条采样，
  写进每一行会重复几百遍，而且查"本月报警几次"要写 `GROUP BY`。一次告警一行，查询和展示都直接。
- **启动时清理 `end_ts IS NULL` 的遗留记录**：上个进程被 `kill -9` 时状态机跟着消失，
  这条记录永远不会被收尾，网页上会一直挂一条假告警。启动时把 `end_ts` 补成 `start_ts`。

## 6. 编译与运行

```bash
sudo apt install build-essential libsqlite3-dev

make                 # 编出 ./gw
./gw -d /dev/ttyUSB0 -b 115200 -f ./gw.db -p 8080
```

然后浏览器打开 `http://<这台机器的IP>:8080/`。
启动时会自动打印本机局域网 IP，手机上也能看。

参数：

| 参数 | 说明 | 默认 |
|---|---|---|
| `-d` | 串口设备 | `/dev/ttyUSB0` |
| `-b` | 波特率 | `115200` |
| `-f` | SQLite 文件 | `./gw.db` |
| `-n` | 多少条提交一次事务 | `20` |
| `-p` | HTTP 端口，**填 0 关闭网页** | `8080` |
| `-q` | 安静模式，不打印每帧 | 关 |

### MQTT 订阅（第 4 步，独立进程）

```bash
sudo apt install libmosquitto-dev mosquitto mosquitto-clients

make mqtt_sub                                    # 编出 ./mqtt_sub
./mqtt_sub 127.0.0.1 1883 env_mqtt.db            # broker  port  db 文件（三个参数全部可省，有默认值）
```

参数是**位置参数**，全部可省略，默认 `127.0.0.1 1883 env_mqtt.db`：

| 位置 | 含义 | 默认 |
| --- | --- | --- |
| `$1` | broker 地址 | `127.0.0.1` |
| `$2` | 端口 | `1883` |
| `$3` | SQLite 文件 | `env_mqtt.db` |

`mqtt_sub` 和 `gw` 是**两个独立进程，各自一个数据库文件**（默认 `env_mqtt.db` 与 `gw.db`）：

| 进程 | 数据来源 | 数据库文件 | 写入的表 |
| --- | --- | --- | --- |
| `gw` | 串口（CC2530 协调器直连） | `gw.db` | `env_data`、`alarm_event` |
| `mqtt_sub` | MQTT（ESP32 网关上云） | `env_mqtt.db` | `env_data_mqtt` |

分成两个文件而不是同一张表，是因为两条链路的**完整性不一样**：
串口链路本地直连几乎不丢，MQTT 链路有 QoS1 重传（可能重复）也有断线丢包（可能缺失）。
混在一起就再也分不清「这条是准的还是有疑问的」。

调试期两条链路同时跑，正好能**交叉验证**——同一时刻两边的温湿度、`lux`、`gas` 应该几乎一样：

```bash
# 两个文件分别查，或者用 ATTACH 拼起来一起看
sqlite3 gw.db "ATTACH 'env_mqtt.db' AS m;
  SELECT a.ts, a.temp_x10, b.temp_x10, a.gas, b.gas
  FROM env_data a JOIN m.env_data_mqtt b ON a.ts = b.ts
  ORDER BY a.id DESC LIMIT 5;"
```

订阅主题是 **`zigbee/+/env`**（用 `+` 通配一层，所以 `zigbee/node1/env`、`zigbee/node2/env` 都能收到），
消息体是一个扁平 JSON：

```json
{"node":1,"temp":194,"hum":590,"lux":551,"gas":39,"pir":0,"relay":0}
```

`temp` / `hum` 是 **×10 定点整数**（194 = 19.4°C），与数据库里 `temp_x10` / `hum_x10`
的存储口径完全一致，避免在服务端做浮点。字段越界（`lux`/`gas` > 1023、
`pir`/`relay` 不在 0/1、`node` = 0）整条丢弃。

运行起来的输出：

```
[DB] 已打开 env_mqtt.db（表 env_data_mqtt）
[MQTT] 连接 127.0.0.1:1883 ...
[MQTT] 已连接 broker，订阅 zigbee/+/env (QoS1)
---- 5s: 收到=5 入库=5 解析失败=0 疑似重复=0 ----
```

回调里只把消息塞进内存缓冲，主循环攒够 20 条才提交一次事务——
和 `gw_db.c` 是同一个思路，避免在网络线程里做 SQLite IO。

每帧那一行里 `gas=原始 med=滤波 base=基线 N%` 四段是刻意并排的：

没有这几段，出了误报就只能猜。

### HTTP 接口

| 路径 | 返回 |
|---|---|
| `GET /` | 网页（14.7KB，内嵌在二进制里） |
| `GET /api/latest` | 最新一帧 + 加工结果 + 告警状态，**读内存快照，0 延迟** |
| `GET /api/history?limit=60&node=0` | 最近 N 条，时间正序，`node=0` 表示不限 |
| `GET /api/stats` | 帧数 / 坏帧 / 入库 / 库行数 / 告警次数 / uptime |
| `GET /api/alarms?limit=20` | 最近 N 次告警，**时间倒序**（最新在上） |
| `GET /api/cmd?v=1` | **第 5 步**：v=1 吸合、v=0 断开，立即返回不等结果（原因见 6.7） |


## 6.5 M3 的核心设计：实时走内存，历史走库

这是整个 M3 唯一需要想清楚的事。

```
串口 ──► 解析 ──┬──► gw_latest（内存，几十字节）──► /api/latest
                └──► SQLite（攒 20 条提交）───► /api/history
```

**为什么实时值不能查 SQLite？**

gw_db 为了省 fsync，是**攒 20 条才提交一次事务**的。1 秒 1 帧 →
未提交的数据最多 19 条。而 SQLite 的隔离性保证：**未提交的行别的连接看不见**。
所以如果 `/api/latest` 直接 `SELECT ... ORDER BY id DESC LIMIT 1`，
网页上显示的"当前温度"最多会滞后 **19 秒**。

环境监测页面上显示 19 秒前的温度，是硬伤。

**所以：**

| | 数据源 | 延迟 | 为什么 |
|---|---|---|---|
| `/api/latest` | 内存快照 `gw_latest` | 0 | 解析完立刻更新，单线程无锁 |
| `/api/history` | SQLite | 最多 19 秒 | 只用来画趋势，差几秒看不出来 |

**顺带解决了并发问题**：因为串口和 HTTP 在同一个进程、同一个线程、同一个 epoll 里，
整个程序**不需要任何锁**。如果用「HTTP 起独立线程」的写法，就得上互斥锁保护
快照和 sqlite 句柄，复杂度和出错面都会上去。

**对应的一个坑（已经踩过）**：`gw_db_total_rows()` 开头会先 commit 再 COUNT。
如果 HTTP 每 2 秒调它一次，等于每 2 秒提交一次事务，批量提交就废了。
所以另外加了一个 `gw_db_count_rows()`，纯查不提交。

## 6.6 M4 的核心设计：为什么不能写死阈值

这一节是 M4 全部的设计理由，面试问"你的告警怎么判"就照这个答。

### 问题：MQ-2 的 ADC 值没有绝对意义

MQ-2 是半导体气敏元件，输出受**温度、湿度、加热丝老化、器件个体差异**四个因素影响。
同一个房间，冬天洁净空气读 35，夏天可能读 60；换一块模块，同样空气可能读 80。

所以「gas > 600 报警」这种写法，**换个季节或换块板子就失效**，而且失效时不会报错，
只会在不该报警的时候沉默、在该报警的时候乱叫。

### 解法一：相对基线的倍数

判定只用 **`gas / 基线`**：

| 参数 | 值 | 含义 |
|---|---|---|
| `ALARM_TRIG_PCT` | 250 | 涨到基线的 2.5 倍 → 疑似烟雾 |
| `ALARM_CLR_PCT` | 150 | 降到 1.5 倍以下 → 才考虑解除 |

基线由慢速 EMA 提供（`τ = 600` 帧 ≈ 10 分钟），会跟着环境慢慢漂。
**换板子、换季节都不用改代码。**

### 解法二：整数不能直接用 EMA —— 会卡死

`base += (gas - base) / tau` 是标准写法，但在整数上有个致命问题：

```
base = 3500（×100 定点，即 35.00）
gas  = 3600（36.00）
差   = 100
100 / 600 = 0      ← 整数除法
```

基线**永远不动**。差值小于 `tau` 时步长恒为 0，这是经典整数死区。

所以用**余数累积版**：

```c
b->acc += target - b->base_x100;          /* 余数攒起来 */
step = b->acc / b->tau;
if (step != 0) { b->base_x100 += step; b->acc -= step * b->tau; }
```

600 帧后 `acc` 攒够 600，步长变 1，基线挪一格 —— 长期平均完全正确。
`test_filter.c` 的用例 [7] 专门盯这个：`tau=600` 时喂 600 帧 36，基线必须从 35 走到 36。

### 解法三：三档状态 + 连续帧确认（抗单帧干扰）

```
NORMAL ──gas ≥ 2.5倍──► WARN ──连续 3 帧──► ALARM
   ▲                                          │
   └──────────连续 10 帧 ≤ 1.5倍───────────────┘
```

为什么要 WARN 这一档：单帧越线很可能是水汽、开关电源瞬时负载。
要求**连续 3 帧**确认，偶发尖峰过不去。3 秒延迟对烟雾告警无所谓，但误报率大幅下降。

### 解法四：迟滞（双阈值）防抖动

进出用同一个阈值的话，gas 在 2.5 倍附近抖动会疯狂反复报。
把解除线拉到 1.5 倍，**1.5~2.5 倍是死区**：一旦报警就必须明显降下来才解除。

### 解法五：中值滤波吃掉孤立尖峰

5 帧窗口取中间值（奇数窗口，偶数要取平均会引小数）。
窗口内一个孤立尖峰必被挤掉；持续 3 帧以上的真实烟雾正常透传。
`med` 和 `raw` **都要暴露**给网页和日志 —— 光给一个数说服不了人，并排才看得出滤波干了什么。

### 顺序陷阱：判定必须在基线更新之前

```c
med = gw_medfilt_push(&ctx->med, e->gas);
if (!gw_baseline_valid(&ctx->base)) gw_baseline_update(&ctx->base, med, 0);
ev  = gw_alarm_feed(&ctx->alarm, med, &ctx->base, ts);      /* ← 用旧基线判 */
gw_baseline_update(&ctx->base, med, ctx->alarm.state == ALARM_ST_ALARM);
```

如果先更新基线再判：烟一来，基线立刻被这一帧的高值抬上去，
`gas / 基线` 永远够不到 2.5 倍 —— **烟越浓基线涨越快，形成自锁，永远不报警**。
这是自适应基线的头号陷阱。告警期间还要 `freeze` 基线，从根上避免"真烟雾持续 10 分钟
被当成新常态、告警自己消失"。

## 6.7 第 5 步：网页远程控制（M5-1）

网页上两个按钮，按下后一道命令要穿过五段链路：

```
浏览器  GET /api/cmd?v=1
  └─ gw（本机）          gw_cmd.c 用裸 socket 连 127.0.0.1:1883
       └─ mosquitto      PUBLISH 到 zigbee/node1/cmd，payload 是单字符 "1"
            └─ ESP32     订阅者；收到 "1" 转成字节 0x41，从 UART1 写出去
                 └─ 协调器  P0_5 收到字节 → 单播给终端，隔 200ms 重发共 5 次
                      └─ 终端  relay_set(1) → P1_3 拉高 → 继电器吸合
```

任一段断了，现象都是"继电器不动"。所以每一段都留了独立的观察点：

| 段 | 怎么确认它通了 |
|---|---|
| gw → broker | `/api/cmd` 返回 `{"ok":1,...}`；失败会直接返回中文原因 |
| broker → ESP32 | ESP32 串口打 `[收到命令] payload='1'` |
| ESP32 → 协调器 | 协调器 **LED1 快闪 3 下**（常亮约 0.4 秒 = 还在广播，不是单播） |
| 协调器 → 终端 | 终端屏幕上的继电器图标 + 下一帧上报的 `RLY=ON` |
| 终端 → 继电器 | 继电器"咔"一声（这个最直接，声音是即时的） |

### 三个刻意的取舍

**① 自己拼 MQTT 报文，不用 libmosquitto。**
只需要 CONNECT → CONNACK → PUBLISH → DISCONNECT 四步，QoS0，一共 40 多个字节。
引库要多装 `libmosquitto-dev`，还要处理它的回调线程；而网关是单线程 epoll 主循环，
阻塞行为必须自己可控。拼包是纯函数（`gw_cmd_build_*`），
`tests/test_cmd.c` 里对着标准字节串逐位断言，不需要 broker 就能验。

**② 用 GET 不用 POST（这是取舍，不是疏忽）。**
本网关的 HTTP 解析刻意只读请求头（读到 `\r\n\r\n` 就停），不为一个按钮去实现
`Content-Length` 读取循环。代价是"GET 改状态"不符合 REST 惯例，
浏览器预取 / 地址栏敲一下都可能触发。因此加了两道限制：
参数必须显式给 `v=1` 或 `v=0`（缺省直接拒绝，不猜），且只在内网使用。
真要上公网，第一件事就是改 POST + CSRF token。

**③ 立即返回，不等命令落地。**
命令过三段最长约 1 秒，HTTP 阻塞等会让按钮一直转圈。
而页面本来就每 2 秒轮询 `/api/latest`，继电器那一格下一轮自己就变了。
所以接口返回的 `ok` 只代表"命令已交给 ESP32"，**真正的结果看网页上「继电器」那一格**。
按钮文案里写的就是这句，避免看到"已发"而继电器没动时误判成成功。

### 实测结果（2026-10-28 整链跑通）

协调器固件从 v5 改到 v6 之后（单播 + 2 包 / 1000ms + 关掉 `AF_ACK_REQUEST`）：

| 指标 | v5（5 包 / 200ms + APS 确认） | **v6（2 包 / 1000ms，无 APS 确认）** |
|---|---|---|
| 命令命中率 | 8 / 8，但延迟长 | **8 / 8（100%）** |
| 终端是否掉线 | 多次退网重建，屏幕定格 | **全程不掉线**，`帧 #432→#905` 连续无断档 |
| 命令→继电器动作延迟 | 1.5~4 秒 | **1~2.6 秒** |
| 坏帧率 | — | **3 / 900 = 0.33%**，`丢弃=0` |

延迟下限由终端 `POLL_RATE=1000`（休眠终端每秒问一次父节点）决定，不是 bug。

### 参数

默认连 `127.0.0.1:1883`，主题 `zigbee/node1/cmd`。三个都能用环境变量覆盖，
换 broker 地址不用重新编译：

```bash
GW_MQTT_HOST=127.0.0.1 GW_MQTT_PORT=1883 \
GW_CMD_TOPIC=zigbee/node1/cmd ./gw -d /dev/ttyUSB0 -p 8080
```

systemd 托管时加在 unit 里：

```ini
Environment=GW_MQTT_HOST=127.0.0.1
```

## 9. 面试可能问到的设计点

**为什么用 epoll 而不是 select？**
select 的 fd_set 上限 1024、每次调用都要把整个集合从用户态拷进内核、返回后还要线性扫描。epoll 用红黑树管 fd、用就绪链表返回，O(1) 拿就绪事件，且 fd 数量不受限。

**为什么用 signalfd 而不是 signal()？**
信号处理函数里只能调用异步信号安全函数（不能 printf、不能 malloc），限制多且容易写出隐患。转成 fd 后进 epoll，所有逻辑都在主循环里，同步、可调试。

**为什么帧解析要"跳到下一个帧头"而不是逐字节 drop？**
逐字节 drop 在遇到整段垃圾时要循环几千次 `memmove`，O(n²)。直接定位下一个帧头是 O(n) 一次搞定。只有"后面完全没帧头"时才退化成逐字节，保证循环一定能退出。

**为什么数据库用 WAL？**
M3 会有 HTTP 线程同时读库。默认的 rollback journal 下读写互斥，查询会把采集写入卡住。WAL 允许一写多读并行，正好匹配"1 秒 1 条写 + 网页频繁查"的场景。

**串口读到的数据为什么不能直接当帧处理？**
串口是字节流，没有消息边界：一次 `read()` 可能拿到半帧、两帧半、或者中间夹着上电毛刺。所以必须有应用层帧同步，这是所有串口协议栈的必答题。

**为什么 HTTP 服务自己写，不用 libmicrohttpd / mongoose？**
这里只需要 4 个 GET 接口，不解析表单、不处理 POST、不需要 TLS。引框架要多带几万行代码，
而且框架通常自带线程池 —— 那就得处理跨线程数据同步，把"单线程无锁"这个最大优点丢掉。
自己写 400 行，每个字节都能讲清楚，这在求职项目里是加分项而不是减分项。

**为什么用 `Connection: close` 而不是 keep-alive？**
keep-alive 要维护每连接的状态机（读到哪、上个请求完没完、空闲计时），
而一个页面只有 2 个 JSON 请求、2 秒一轮。局域网里三次握手的开销是微秒级，
换来的是不需要状态机。真要扛高并发长连接，就得加 `EPOLLOUT` 半写状态机，
那是另一个复杂度等级，这个项目用不上。

**网页为什么要打进二进制？**
网关定位是"拷一个 `./gw` 过去就能跑"，不该依赖 html 文件躺在某个相对路径下
（换工作目录就 404 了）。代价是改网页要重新编译：`make web && make`。

**写 HTTP 最容易犯的错是什么？**
`Content-Length` 和实际 body 长度对不上。对不上时浏览器不会报错，
只是一直转圈等剩下的字节，非常难查。所以 `tests/test_http.c` 里
**每个用例都会校验这两个数相等**。

**烟雾告警为什么不用固定阈值？**
MQ-2 的 ADC 值受温度、湿度、加热丝老化、器件个体差异四重影响，没有绝对意义。
「gas > 600 报警」换个季节或换块模块就失效，而且失效时不报错 ——
只在该报的时候沉默、不该报的时候乱叫。
所以判 `gas / 基线` 的倍数（2.5 倍触发 / 1.5 倍解除），基线由慢速 EMA 自适应提供。
代价是多两个模块，换来的是换板子换季节都不用改代码。

**自适应基线最容易踩什么坑？**
两个。① **整数死区**：`base += (gas-base)/tau` 在差值小于 `tau` 时步长恒为 0，
基线永远不动。必须用余数累积（`acc` 攒够再挪）。
② **自锁**：如果先更新基线再判阈值，烟一来基线立刻被抬上去，
`gas/基线` 永远够不到触发线 —— 烟越浓基线涨越快，**永远不报警**。
所以顺序必须是「先判阈值、再更新基线」，而且告警期间要冻结基线，
否则持续 10 分钟的真烟雾会被当成新常态、告警自己消失。

**为什么要三档状态 + 迟滞？**
单帧越线很可能是水汽或电源瞬时负载。加一档 WARN 要求连续 3 帧确认，
把偶发尖峰挡在门外。进出用同一个阈值则会在阈值附近疯狂反复报，
所以解除线拉到 1.5 倍，中间 1.5~2.5 倍是死区 —— 一旦报警就必须明显降下来才解除。

**告警为什么要单独一张表？**
告警是**事件**不是**采样**。一次告警横跨几十秒、几百条采样，
写进每一行会重复几百遍，查"本月报警几次"还要写 `GROUP BY`。
一次告警一行，`end_ts` 为 `NULL` 表示进行中，查历史和展示都直接。
配套要做的是**启动时清理遗留的 `end_ts IS NULL` 记录** ——
上个进程被 `kill -9` 时状态机跟着消失，这些记录永远不会收尾，
网页上会一直挂着一条假告警。

**为什么远控放最后**：它要同时改 CC2530 固件（加命令帧解析 + 上报继电器实际状态）

比丢数据更容易误导人。这条链路上丢几秒数据和造一个假象，后者更糟。
