它动了，但不是我要的动

2026-11-13 · 已闭环 排障实录 日志 误判 方法论

前四篇写的都是"最后是怎么做的"。这一篇写中间是怎么错过来的。

为什么不写"顺利的版本"：因为顺利的版本不包含任何可复用的判断。 真正让人卡住一整天甚至一整晚的，从来不是"这段代码怎么写"， 而是"现象摆在眼前，我不知道该怀疑哪一层"。 这次上机一共出现了十三次误判， 其中七次是我把原因猜错了，两次是我修错了方向（修完之后更糟）。

下面按故障出在哪一层分组，而不是按时间顺序—— 时间顺序是给当事人看的，分层才给后来的人用。

零、先给一张分层图

这套链路上有四个可以出问题的层次。它们的症状特征完全不同， 但都表现为"它不动"。如果没有这张图，人会很自然地在最熟悉的那一层反复找。

这张图是事后才画出来的。当时没有它，所以我做的第一件事就是 在第四层（生命周期）的问题上，反复重装第一层（会话）的东西—— 重新 scp、重启服务、换端口，做了十几遍，问题一次都没变。

一、第一组：话没通

误判 1 · 遥控器推不动风机，我以为是遥控器没连上

最早的验证脚本里有个 watch-rc，专门盯遥控器通道。 拨杆的时候它只打出一行： 

[状态] mode=LOITER
[状态] mode=LOITER
[状态] mode=LOITER

一个通道值都没有。第一反应是"遥控器没连"或"接收机没对频"。 但这个判断很容易被推翻：飞控状态能读到 LOITER，说明链路是通的—— 连不上飞控，mode 也读不出来。

真正的原因是：脚本用的是 REQUEST_DATA_STREAM 这个 已经被 PX4 1.16 废弃掉的旧订阅接口。 消息发出去不报错，飞控只是不理会。 于是脚本"订阅成功"了，却永远收不到 RC_CHANNELS。

!
废弃接口的失败方式是"静默"。 它不返回错误、不抛异常，只是从此没有数据。 所以只要看到"连接成功但内容永远为空"，第一个要怀疑的就是协议版本， 而不是物理链路。改成 MAV_CMD_SET_MESSAGE_INTERVAL，并每隔几秒重发一次（防止被飞控重置）， 通道值立刻就有了。

误判 2 · 文件传不过去，我以为是网络断了

scp 一直超时。查了半天无线信号、防火墙、SSH 配置， 最后发现是我自己给错了 IP。

地址实际用途能不能 scp
10.41.10.1 eth0，直连飞控的那条网口的地址 不能——那是给 MAVLink 用的，不是给人登录的
192.168.110.180 wlan0，板子接路由器的地址 能——日常 SSH / scp 全走这个

这两个地址很容易混，因为两个都能 ping 通、两个都"看起来像板子"。 判据只有一个：能不能 SSH 上去。 能登进去的那个，才是给人用的。

误判 3 · 传了四次才对——因为我一直在核对文件名

这一条最典型。改完代码传上去，跑起来报 unrecognized arguments: --rod-invert。 第一反应是"参数写错了""代码没编过"。

实际情况：板子上跑的是旧文件。而我确认的方式是看 ls -l 的文件名——文件名当然一样，因为它就一直叫那个名字。

真正致命的细节在路径上：在 Git Bash 里用 "D:\雷电鸟实习\...\代码\px4_actuator_client.py" 这种反斜杠中文路径， \ 被当作转义符吃掉了，路径解析失败，scp 传的是别的东西或者干脆没传， 但终端只给一行超时，看起来像是网络问题。

i
换来的一条硬规则：落地文件必须用哈希确认，不能用文件名、不能用时间戳、不能用大小截图。 这次四个版本的哈希是这样对上的—— f063f662 / 61198 字节（无方向修正）→ 9aca49b7 / 62458（第一次修方向，修错）→ d915aa1c / 61624（删掉开关，只改键盘）→ 4e5d7144 / 62730（接管即作废）。 板子上一敲 sha256sum，前 8 位一对比，"到底是不是新版"这个问题就不再需要猜。

误判 4 · 加了个 1，整条命令根本没执行

复制命令时前面多带了一个字符，变成 1sudo systemctl stop px4fan。 bash 报 1sudo: 未找到命令，然后继续执行下一行—— 于是停下来看：服务没停、端口还占着、脚本连不上飞控， 而屏幕上全是"参数不认识""连不上"之类的错误。

看起来像一个复杂的复合故障，实际是第一行根本没跑。 这类问题的判据很简单：报错之前那条命令，有没有回显成功。 systemctl stop 成功是静默的， 所以更稳的写法是先 systemctl is-active 看一眼，再从 active 变 inactive。

误判 5 · 参数改了，但"没生效"

把伸缩杆那个 AUX 口从"遥控器直通"改成"板子控制"，QGC 里点了保存、数值也变了， 结果什么都没变——遥控器还能直接驱动杆子。

原因：PWM_AUX_FUNC* 这类参数只在飞控启动初始化 PWM 输出时读一次。 热改参数不会重新绑定输出通道，必须重启飞控。 而且重启后要再查一次，确认它真的写进了 flash，没有变回原值。

误判 6 · 下拉菜单里差一个选项，就是完全不同的东西

同一个下拉框里有两个长得很像的选项：一个是给"电机 8"，一个是给"执行器通道 2"。 选错了，界面上都显示"已配置"，但板子发下去的指令落在一个没人听的通道上。

选项数值含义
Peripheral via Actuator Set 2302✅ 板子的第 2 路执行器指令
Peripheral via Actuator Set 3303那是风机那一路，杆子接上去会跟着风机转
RC AUX 2409遥控器直通（改之前的原值）

正确的确认方式不是看界面，而是跑 probe 读飞控自己认为这个口在干什么： 必须出现 Offboard Actuator Set 2 和 已配 Offboard Actuator: AUX2=Set2, AUX3=Set3 这一行。

二、第二组：动了，但不对

这一组是全部十三次里最贵的。因为第一组的故障"不动"， 而这一组的故障"动了"——动了就会让人以为成功了。

误判 7 · 方向反了，而我第一次只改了一半

键盘敲"向上"，杆子往下走。当时的判断是"代码里映射写反了"， 于是去改键盘那一支。

但我漏了一个问题：这个"向上/向下"是谁定义的？ 键盘和遥控器是两个独立的输入源， 它们各自到脉宽的映射本来就是分开的两段代码。 我只验证了键盘是反的，就默认"两边都反"。

误判 8 · 为了修方向，我加了一个把两边一起翻的开关

这是这一整晚最糟的一次。我加了一个 --rod-invert， 以中位为轴做镜像：1000↔2000、1500 不动， 并且键盘和遥控器同时过这个镜像。

结果：键盘对了，遥控器反了。 因为遥控器本来就是对的——它往上拨给低档、杆子向上，方向一直是对的。 我用"一把剪刀"剪了两边，把原本正确的那一边剪坏了。

×
根因不是"方向反了"，是"我没有先测出两个输入源各自的原始方向"。 正确顺序应该是：先单独记录每个输入源在没有任何修正时的行为， 写进一张表，再决定改哪一段。 我跳过了这一步，直接开始改，于是把"一个明确的 bug"变成了"两个互相矛盾的 bug"——后者更难查， 因为两个方向相反的错会互相掩护。

最终的修法很短：删掉 --rod-invert 整个开关，只改键盘那一支的两个常量， 遥控器一个字不碰。删掉之后两边的行为第一次一致。

输入源操作下发脉宽杆子动作
键盘ru1000向上
键盘rm1500停
键盘rd2000向下
遥控器往上拨（低档 1050）1000向上
遥控器居中（1500）1500停
遥控器往下拨（高档 1950）2000向下

误判 9 · 遥控器松手之后，杆子自己又走回去了

这个现象第一次出现时，我以为是"遥控器回中没被识别"。日志否掉了这个猜测： 

[仲裁] CH6=1050us -> 伸缩杆 1000us [低档]      ← 遥控器夺权，杆子向上
[仲裁] CH6=1500us -> 伸缩杆 1500us [中位]      ← 回中，停住了
[仲裁] CH6=1500us -> 伸缩杆 2000us [中位]      ← 下一拍：怎么又往下了？

遥控器这边完全正常，问题在板子那边： 板子之前敲过一条 rd（向下），这条指令在遥控器介入时只是被暂时压住，没有被作废。 遥控器一回中，压住它的力消失了，旧指令原地复活。

✓
"接管"和"作废"是两件事。 接管是"这一拍听我的"，作废是"你那条指令从此不存在"。 只做前者，就会得到一个在松手之后才开始执行旧动作的机器。 在会动的设备上，这是最坏的一类行为——它发生在你以为事情已经结束的时候。

改法只有一行：遥控器一旦离开中位，就把板子当时的方向指令清零， 让它和"停"变成同一个值。这样回中读到的是"停"，而不是那条旧指令。

误判 10 · "锁住当前速度"这个功能，在弹簧杆上根本不可能重复

这个设计被推翻过三次，最后彻底删掉了。技术上最有力的证据是这一条：

操作摇杆推到锁存到的值
快速弹一下约 13001300
慢慢推过去约 10811081

锁存用的是"松手那一拍采样到的值"，而采样时刻取决于手速。 所以同一个意图得不到同一个结果。

一个设备如果做不到"同样的动作产生同样的结果"，它就没法被信任—— 尤其在它下面挂着 100 公斤的东西、旁边是光伏板的时候。 最后收敛成一条规则：遥控器一回中，就停；板子要转，重新下指令。 一句话说完，没有内部状态需要理解。

三、第三组：该停的时候没停

误判 11 · 服务停了，电机还在转

做成开机自启之后发现：systemctl stop px4fan， 进程没了、服务显示 inactive，风机还在转。

原因是 systemd stop 发的是 SIGTERM， 而脚本的"归零"写在 finally 里。 Python 收到 SIGTERM 时默认直接终止，不走 finally—— 于是最后一条 PWM 指令永远发不出去，飞控保持最后一个值。

!
"优雅退出"不能依赖 finally。 正确做法是让信号处理函数只置一个标志位， 由主循环自己发现标志、正常走完收尾、再退出。 改完后的日志末尾会多出一行，这是唯一能证明它真的停了的证据： [安全] 已下发 -1.0 = 1000us，风扇应停转；伸缩杆已回中位 1500us（停止）

误判 12 · 服务一跑起来，键盘就没有了

服务模式下 stdin 不是终端，交互指令全部失效； 而手动再起一个进程又会撞上端口已被占用 （同一时刻只能有一个进程绑在那个 UDP 端口上）。

最后的办法是绕开端口：不连飞控，只写一个文件。 客户端往 ~/px4fan/ctl 写一行字就退出， 服务每 50 毫秒读一次、读完即删。这样它和服务天然共存， 也不需要多一条 MAVLink 连接。后来在这上面又包了一层 rod up / fan 35 这样的短命令。

误判 13 · 日志"全绿"，我就以为通过了

这是十三次里最应该记住的一次——因为它不是 bug，是判断失误。

某次上机的日志里，三档识别全对、风扇没被干扰、退出归零正确， 我当时就准备往下推进了。但回头看那份记录，有三个关键项根本没被验证： 中位 1500 是不是真的能停住、杆子有没有真的动、 超时保护有没有真的触发（那次单次最长只有 8.5 秒，而阈值是 15 秒，压根没到）。

×
"日志里没有报错"和"这一项通过了"是两件完全不同的事。 一条日志只能证明它打印出来的那件事。 凡是判据里写了"实际动作"的项，就必须有一次能触发它的操作， 否则那一行永远只是"还没轮到它出错"。

四、怎么读一条刷屏日志

这套脚本每秒打两行，跑五分钟就是六百行。 但真正有信息量的只有状态发生跳变的那几行。 我的办法是把它压成一张时间轴表，只留跳变点：

时刻日志关键字段它在证明什么
9.0s CH6=1050us -> 1000us [低档] 遥控器给 1050，实际下发 1000 —— 量化生效，不是透传
10.5s CH6=1500us -> 1500us [中位] 回中即停，没有回到键盘上一次设的值
12.0s CH6=1950us -> 2000us [高档] 反向量化，1950 → 2000
27.0s 已运行 15s，强制回中位 + 🔒超时保护中 12.0 起算，15 秒后准时截断 —— 保护真的会触发
27.0 → 55.1s 一直拨高档，输出死守 1500 保护期内拨杆无效 —— 锁定有效
74.1s 高档 → 低档，中间划过中位 回中位自动解锁 —— 反向操作能走
89.1s 第二次 已运行 15s 保护可以重复触发，不是一次性的
Ctrl-C 伸缩杆已回中位 1500us（停止） 双路同时归零 —— 退出不留动作

这张表只用了一个方法：每一行都必须回答"它在证明哪一条设计"。 答不出来的行，就是噪声；答得出来的行，一条也不能少。

顺带说清一个看起来像 bug 其实不是的现象： 用键盘敲 ru 时，超时保护触发后不会出现 🔒。 因为键盘不会拨动遥控器，通道一直停在中位， 脚本下一拍就判定"已回中位"并自动解锁——所以现象是"打印保护、杆子停下、状态回到中位"。 🔒 那个锁只出现在遥控器一直拨着不放的时候。

六、三条带得走的规则

  1. 先分层，再怀疑。 "不动"有四个完全不同的层次会导致，每一层的确认手段不一样。 在错误的层上做的每一次尝试，都是零信息量的。
  2. 核对用哈希，不用名字。 文件名、时间戳、截图大小都可能骗人，哈希不会。 这一条能省掉后面所有的"是不是又把旧文件跑了一遍"。
  3. 改之前先记录"它现在的行为"，再动手。 十三次里有两次是"因为修错方向而变得更糟"， 两次都发生在没有先写下"原状"的时候。 同时改两个变量，等于放弃定位能力。

七、还没做的

  • 没飞过。所有验证都是吊装地面状态，振动、气流、供电波动是另一套输入。
  • 行程没量准。 超时现在按 12 秒给，真实全行程秒数还是要掐表测一次。
  • 硬件兜底没装。 限位开关 + 继电器还是纸面方案—— 杆子顶在机械限位上时，软件超时是唯一的断电手段。
  • 那十三次里，有七次本可以靠"先测原状"避免。 这条写在这里，提醒下一次的自己。
