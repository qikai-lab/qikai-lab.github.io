第 2 周：ZigBee 组网，以及一个差点蒙混过关的设计错误

2026-10-23 · 第 2 步已通过 Z-Stack OSAL 设计错误

组网本身比预想的顺利。GenericApp 工程有两个编译配置， CoordinatorEB 烧协调器板、EndDeviceEB 烧终端板， 上电之后协调器自动建网，终端自动入网，串口每秒吐一帧数据。 从「两块板子各自跑」到「一块板子收另一块板子的数据」，中间只花了半天。

真正费时间的是之后的一次测试——我顺手把协调器断电，想看看终端会怎样，结果发现终端整个停住了。 不是「发不出去」，是连采都不采了，屏幕上的数字凝固在断网前那一帧，一动不动。

这件事暴露的问题，比组网本身重要得多。

一、先看最终跑成什么样

项目结果
协议栈版本Z-Stack 2.5.1a（课程配套版本，不是 3.0.1）
编译器IAR EW8051 6.0 Evaluation
工程Projects/zstack/Samples/GenericApp/CC2530DB/GenericApp.eww

关于版本：网上大部分 CC2530 教程用的是 Z-Stack 3.0.1（配 IAR 8.10+）， 而课程配套源码是 2.5.1a。这两者的 GenericApp.c 结构接近但函数签名有差异， 照抄 3.0.1 的代码进 2.5.1a 会编译报错。先确认版本再搜资料，能省一整天。

二、那个「顺手一试」暴露的设计错误

先把现象描述准确，因为后面的定位全靠它：

  • 协调器断电 → 终端板仍在运行（心跳灯在闪，按键有反应，继电器能手动开关）
  • 但屏幕上温湿度、光照、烟雾全部冻结，不再变化
  • 把协调器重新上电 → 数据立刻恢复，看起来一切正常

第二、三条合起来是决定性的：冻结和恢复都跟着协调器的状态走。 说明不是传感器坏了、不是 I2C/单总线时序挂了、也不是主循环死了——是某段跟网络状态绑在一起的代码没跑。

根因：一个定时器管了两件事

原来的代码结构是这样的（enddevice.c）： 

/* 收到状态变化事件时 */
if ( GenericApp_NwkState == DEV_END_DEVICE ) {
    /* 入网成功 → 启动 1 秒周期定时器 */
    osal_start_timerEx( GenericApp_TaskID,
                        GENERICAPP_SEND_MSG_EVT,
                        ENDDEVICE_SEND_MSG_TIMEOUT );
}

/* 定时器到点 */
if ( events & GENERICAPP_SEND_MSG_EVT ) {
    SyncData();                          /* ← 读传感器 + 刷屏 */
    AF_DataRequest( ... );               /* ← 发给协调器 */
    osal_start_timerEx( ... );           /* 续下一次 */
    return ( events ^ GENERICAPP_SEND_MSG_EVT );
}

「读传感器」和「发数据」被塞进了同一个定时器回调。 而这个定时器的启动条件写的是「入网成功」。

于是逻辑变成了：没有网络 → 定时器不启动 → 回调不执行 → 传感器不读。 一个纯本地动作，被一个远程条件卡住了。这个耦合在功能演示阶段完全看不出来—— 因为演示时协调器一直开着，网络一直在。只有主动把它弄断，问题才会浮出来。

✕
这不是 bug，是设计错误。 bug 是「代码没按写的意图运行」；这里是「代码完全按意图运行了，但意图本身错了」。 这类问题调试器帮不上忙，因为没有任何一行代码行为异常。

三、重写：把采集和上报彻底拆开

正确的模型是：采集是本地职责，上报是网络职责，两者没有因果关系。 入网了就该发，没入网就只采不发。前者不能成为后者的前提。

改动分三处。第一处是把定时器的启动从「入网事件」挪到初始化：

static void GenericApp_Init( uint8 task_id )
{
    ...
    /* 定时器上电就跑，跟网络状态无关 */
    osal_start_timerEx( GenericApp_TaskID,
                        GENERICAPP_SEND_MSG_EVT,
                        ENDDEVICE_SEND_MSG_TIMEOUT );
}

第二处是把回调拆成两段，采集无条件执行、上报加门禁： 

if ( events & GENERICAPP_SEND_MSG_EVT ) {
    SyncData();                          /* 无条件：读传感器 + 刷屏 + 更新本地状态 */

    if ( node_net_state() == NET_ST_JOIN ) {
        AF_DataRequest( ... );           /* 只有入网了才发 */
        s_tx_frames++;                   /* 计数只统计真正发出去的 */
    }

    osal_start_timerEx( ... );
    return ( events ^ GENERICAPP_SEND_MSG_EVT );
}

第三处是给「网络状态」一个明确的判断函数，而不是散落在各处比较枚举：

static unsigned char node_net_state(void)
{
    switch ( GenericApp_NwkState ) {
        case DEV_END_DEVICE:
        case DEV_ROUTER:
        case DEV_ZB_COORD:  return NET_ST_JOIN;   /* 已入网，可发 */
        case DEV_INIT:      return NET_ST_INIT;   /* 正在找网 */
        default:            return NET_ST_DOWN;   /* 掉线 */
    }
}
!
拆的时候踩了一个新坑：一开始我没删 ZDO_STATE_CHANGE 里那句 osal_start_timerEx，只在新位置也加了一句。结果是 同一个 event 上挂了两条定时链，上报间隔从 1.000 秒变成 0.5 秒， 射频占空比直接翻倍。OSAL 的 osal_start_timerEx 对同一 event 是覆盖而不是追加， 但两条链各自续下一次，就变成了两倍频率。挪代码的时候，旧的必须删掉。

顺带搞清楚：应用层到底该不该插手入网

修的时候我一度想「那我在检测到掉线时主动调 ZDApp_StartJoiningCycle() 重建入网好了」。 查源码（ZDApp.c:2853）之后发现这个函数只在 DEV_INIT 和 DEV_NWK_DISC 两个状态下有效，其余状态直接返回 FALSE。

结论是：协议栈自己会周期性重建入网循环，应用层不该插手。 这种「以为要补一脚，其实人家本来就在跑」的情况，在协议栈开发里很常见—— 先读源码确认职责边界，比自己加逻辑靠谱。

四、屏幕上的改动：让「没连上」看得见

修完代码，第二个问题浮出来了：终端不联网的时候，屏幕上没有任何提示。 数据不刷新，和「程序卡死了」在观感上一模一样。这在现场排查时是致命的。

所以加了一行状态行。原来的版面是三行数据 + 一块图片区，改成四行：

行内容说明
1T:24.5C H:58.0%温湿度
2LGT: 512 GAS: 36光照 / 烟雾
3PIR:NO RLY:OFF人体 / 继电器
4NET:JOIN TX: 0048本轮新增：网络状态 + 已发帧数

NET 三档用颜色区分：JOIN 绿色、INIT 黄色、DOWN 红色。 TX 是真正发出去的帧计数——没入网时它就停在那里不动， 而上面的数据还在跳。数据在跳、TX 不动，一眼就是「在采但发不出去」； 两个都不动，才是程序真的卡了。

这个对照关系比任何日志都直观，因为它是同屏、同时、持续更新的。

顺带治好了黑边

加行的时候发现面板底色是纯黑（0x0000），而屏幕边框也是黑的， 视觉上数据区像是「陷进去了」，上下都拖着一条黑影。把面板底色换成深灰 （COLOR_DARKGRAY 0x4208），字背景同步换掉，边框立刻出来了。

另外因为终端版面从 3 行变 4 行，图片区高度从 96 缩到 92， 分隔线跟着上移——但协调器和终端共用同一个 UI 模块， 这行改动会把已经验收过的协调器版面一起挪掉。 所以给协调器单独定义了一个分隔线坐标常量，两边解耦。

i
共用 UI 模块的教训：两块板子共用一套绘制代码时，任何「只改终端」的需求， 都要先问一句「这个常量协调器也在用吗」。能拆成两个常量就拆， 否则每改一次终端，就要重新验收一次协调器。

五、一个纯工程问题：命令行编译不出 hex

用 IarBuild.exe 命令行编译，出来只有 .d51，没有 .hex。 IDE 里点 Build 是有的，命令行没有——原因是 hex 转换那一步依赖 .xcl 链接文件里的输出配置，而相对路径在不同工作目录下解析不到。

解法是写个小脚本，编译前把 .xcl 里的输出路径临时改成绝对路径， 编译完再还原。这样命令行和 IDE 的行为就一致了。

这种事不值得花时间研究原理，但必须记下来——否则下次换了目录又来一遍。

六、这轮真正学到的东西

  1. 「没数据」和「没上报」是两件完全不同的事。 这次的根因就是把它们当成了一件事。判断标准很简单： 拔掉网络，本地功能还完整吗？不完整就是耦合错了。
  2. 演示能跑通，不代表设计是对的。 所有「只在异常路径才暴露」的设计错误，都需要主动构造异常去撞。 这次是顺手断电撞出来的，下次要主动列异常清单。
  3. 挪代码时，旧的必须删。 两条定时链同时跑不会报错，只会让周期悄悄变成一半——这种「不报错的错」最难发现。
  4. 让状态可见，比让状态正确更重要。 程序正确但看不出状态，排查时和死机没区别。多加一行 NET/TX 花的成本极低，救的时间极多。
  5. 先确认协议栈版本再搜资料。 2.5.1a 和 3.0.1 的 API 差异足以让「照抄教程」变成一场灾难。
