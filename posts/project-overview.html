项目全景：这个系统到底长什么样

2026-10-22 · 项目设计 架构 技术选型

手里有一堆硬件：两块 CC2530 开发板、一个 CC-Debugger、一套 Ubuntu 虚拟机。 问题是——这些东西能拼出一个什么样的项目？

这篇记录从「有什么」到「做什么」的收敛过程：最初列出四个候选方案， 最后只留一个；以及留下的这个到底要做出什么效果。

一、项目的一句话定义

i
电池供电的 CC2530 无线节点采集温湿度、烟雾、光照与人体感应， 经 ZigBee 协调器汇聚，由 ESP32 网关转 MQTT 上云， 最终在 Ubuntu 服务器落库、出历史曲线，并能从网页远程控制继电器。

这句话里包含了四个技术层次，每一层对应一类真实岗位能力： 嵌入式裸机开发、无线通信协议、网关协议转换、Linux 服务端开发。 这也是选它作为主项目的原因——一条链路能把四类能力全串起来。

二、四层架构

层 角色 干什么 技术要点
感知层 终端节点 采集数据、执行命令 ADC、单总线、GPIO、低功耗休眠
网络层 协调器 组建 ZigBee 网络、汇聚数据、串口送出 IEEE 802.15.4、Z-Stack、自定义帧协议
网关层 ESP32-S3 串口协议解析 → MQTT 上报；接收下行命令 ESP-IDF、MQTT、BLE 配网、LWT 遗嘱
应用层 Ubuntu 服务器 存库、告警、网页展示、命令下发 termios/epoll、多线程、SQLite WAL、手写 HTTP

为什么中间要加 ESP32 网关

CC2530 本身不能直接上网。协调器只能把数据从串口吐出来，所以需要一个「能上网的东西」转一手。 可选方案有几种：树莓派、ESP8266、ESP32。

  • 树莓派：太贵太重，而且它本身就是台 Linux 主机，跟服务器角色重复了
  • ESP8266：只有一路双向 UART，接串口的同时就没法干别的，做网关能力上限太低
  • ESP32-S3：双核 + 16MB Flash + 8MB PSRAM，一路 UART 收数据、另一核跑 WiFi/MQTT，盈余充足

更重要的是，ESP32 上能做的两件事在简历上有额外价值： MQTT 遗嘱机制（LWT）——设备掉线时 broker 自动广播离线消息，这是真实产品的必备能力； BLE 配网——手机把 WiFi 密码传给设备，而不是写死在固件里。

三、六个可演示的功能

项目最怕「做完了但说不清做出了什么」。所以功能必须是能打开给人看的。 这六条每一条都能现场演示，也都能拍成短视频。

#功能怎么演示用到的技术
1 实时监测 网页上看到当前温湿度/烟雾/光照/人体状态，一秒刷新 串口采集 + HTTP 轮询
2 历史曲线 拖动时间轴看过去 24 小时的温度变化折线 SQLite 存储 + 前端图表
3 超限告警 打火机靠近 MQ-2，蜂鸣器响 + 网页标红 阈值规则 + 环形队列
4 远程控制 网页点「开」，板载继电器吸合，接的灯泡亮 下行命令帧 + GPIO 输出
5 本地显示 不联网、不开电脑，彩屏上照样显示四个传感器值 SPI 驱动 1.44" TFT
6 电池续航 拔掉 USB 只装电池，数据照常上传，测出能跑几小时 低功耗模式 + 周期唤醒

第 6 条是很多人会跳过的，但它恰恰最能体现「这是产品不是玩具」。 一块只能插着 USB 跑的开发板，和一块装两节电池能在房间角落跑一天的节点，说服力完全不同。

四、砍掉的三个方案

最初列了四个候选，最后只留一个。砍掉的理由都很实际：

候选方案为什么砍掉
STM32F103 做两轮自平衡小车 硬件现成，但能力模型太单一——只锻炼 MCU 控制与 PID， 碰不到无线组网、碰不到服务端。与 IoT 应用开发岗的能力要求重叠度低。
RS485 / Modbus 工业数据采集 这是工业自动化方向的典型技能，跟目标岗位的应用场景重叠不多。 时间预算有限，优先投在更相关的地方。
ESP8266 单点联网（传感器直连 WiFi） 做出来是「一个联网的温度计」，没有网络拓扑、没有网关、没有协议转换， 技术深度不够。单 UART 也决定了它没法当网关。
ZigBee 无线环境监测系统 选中 覆盖「节点 → 组网 → 网关 → 服务端 → 前端」全链路， 硬件已具备，缺的只有 ESP32 和电池盒。

选项目的标准不是「难不难」，而是「做完之后，简历上能写出几条对方感兴趣的东西」。 自平衡小车的 PID 调参很酷，但写的出来的是「调好了 PID」； ZigBee + MQTT + Linux 服务端能写出来的是「设计并实现了一套四层物联网数据链路」。

五、五步实施路线

拆成五步而不是一次性做完，是因为每一步都必须能独立演示。 这样即使后面某一步卡住，前面的成果依然完整、依然能拿出去说。

步骤做什么工期完成标志
0 工具链搭建与冒烟测试 — 已完成 串口打出自己写的固件
1 传感器采集 + 彩屏显示 + 串口打印 1~2 周 串口能看到四路传感器数据
2 协调器 + 终端组网 2 周 拔掉 USB 只插电池，协调器仍收到数据
3 Ubuntu 写 C 网关服务 2~3 周 浏览器打开网页能看到实时曲线
4 ESP32 独立 WiFi 上云 1~2 周 整机通电即工作，不依赖电脑
5 告警 + 远程控制 + 低功耗 + systemd 2 周 完整产品闭环

六、Linux 侧的分量

如果只是「用 Python 读串口存进 SQLite，再用 Flask 起个网页」，那 Linux 部分大概只有两百行， 撑不起一个「嵌入式 Linux 应用开发」的岗位描述。

所以第 3 步设计成一个真正的 C 服务 gw-server， 单进程五线程，每个线程负责一类职责：

线程职责关键技术
采集 读串口、拆帧、CRC 校验、送环形队列 termios raw 模式、epoll 边缘触发、USB 掉线自动重连
订阅 第 4 步接入后，改为从 MQTT 收数据 裸 socket 拼 MQTT 报文，或 libmosquitto
存储 批量写 SQLite，事务提交 WAL 模式、预编译语句、批量提交降低 IO
告警 按阈值规则判断，触发蜂鸣器与网页标记 条件变量唤醒、环形缓冲
HTTP 响应网页请求，接受控制命令 手写 socket 解析 HTTP 报文，不用框架

整个服务由 systemd 托管，支持开机自启、崩溃重启、日志进 journald。 设备热插拔、信号处理用 signalfd 转 fd 交给 epoll 统一处理，避免异步信号安全问题。

!
刻意不用 Flask / Node-RED。 用框架搭出来的东西谁都会，但「自己写 socket 解析 HTTP 请求行、头部、响应体」 才能真正体现对网络编程的理解。这部分代码量占整个项目的 60% 以上。

领域技术掌握程度要求
