断电重启之后：把一个 Python 脚本变成设备的一部分

2026-11-13 · 已上电自启 systemd SIGTERM 运维 踩坑清单

功能齐了之后，还有一道坎：它现在只是一个"在终端里活着"的程序。 SSH 一断、终端一关、板子一重启，什么都没了。

这一篇是把它做成"设备的一部分"的全过程：开机自己起来、 没有终端也能下指令、被停止时不留下一个还在转的电机。 顺便把这一路上八个"不报错但没生效"的坑列在一张表里—— 它们分布在不同层，但失败方式一模一样。

一、四件东西组成一个服务

文件作用装到哪
px4fan.service 服务单元：怎么启动、挂了要不要重启 /etc/systemd/system/
px4fan.default 参数文件：开机时脚本收到的全部参数 /etc/default/px4fan
logrotate-px4fan 日志轮转，防止写到撑满磁盘 /etc/logrotate.d/
install_px4fan.sh 一键安装上面三样 + 启用 + 启动 ~/px4fan/deploy/

把参数单独抽成一个文件，是我做完第一版之后补的。 一开始参数直接写在 ExecStart= 那一行里， 结果是：改一个数字要编辑 systemd 单元，改完还得 daemon-reload。 抽出来之后变成 EnvironmentFile=，改参数就是改一行文本 + restart， 不用碰单元文件。 

[Service]
EnvironmentFile=/etc/default/px4fan
ExecStart=/usr/bin/python3 /home/ztl/px4fan/px4_actuator_client.py arbiter $ARB_ARGS
Restart=always
RestartSec=3
i
Restart=always 是一把双刃剑。 它让进程崩了自动拉起来，这在无人值守场景里是必须的； 但同时意味着"你怎么改都改不坏"这件事不存在—— 参数写错了，它会每 3 秒崩溃重启一次，无限循环，而你只能从日志里看出来。 所以配 RestartSec=3 而不是 0：留出一点间隔， 让日志里能看清每一次失败，不至于刷屏到无法阅读。

二、systemctl stop 差点让风扇停不下来

这是这一整套里唯一一个会导致硬件继续动的 bug，值得单独一节。

脚本原本的收尾逻辑是 try / finally：主循环在 try 里， 退出时在 finally 里下发"停止"。 手动按 Ctrl-C 的时候，这没问题——KeyboardInterrupt 会走 finally。

但 systemctl stop 发的不是 Ctrl-C，是 SIGTERM。 而 finally 不保证在收到信号时执行。 进程直接退出，finally 里那句"下发 1000us"根本没跑到。 

[安全] 已下发 -1.0 = 1000us，风扇应停转；伸缩杆已回中位 1500us（停止）
   ↑ Ctrl-C 时会打印这一行

   ↑ systemctl stop 时：什么都没有，风扇继续按最后一个转速转

当时的现场：systemctl stop px4fan 之后，服务确实停了， is-active 显示 inactive，但扇叶还在转。 因为飞控收到的最后一条指令是"1200us"，之后再也没有新的， 而 PWM_AUX_FUNC=303 的意思是"听外部指令"—— 外部不说话了，它就保持最后一个值。

修法不是"捕获信号然后优雅退出"那么简单（信号处理函数里做 I/O 是不安全的）， 而是让信号只改一个标志位，由主循环自己决定什么时候退： 

_TERM = {"stop": False}

def _on_term(signum, frame):
    _TERM["stop"] = True          # 只置标志，不做任何 I/O

signal.signal(signal.SIGTERM, _on_term)

while True:
    ...
    if _TERM["stop"]:             # 由主循环判断，退出路径和 Ctrl-C 完全一致
        break

这样两条退出路径合并成一条，finally 里的归零一定被执行到。 实测下来，stop 之后日志里就是那句熟悉的 [安全] 已下发 -1.0 = 1000us。

!
这是一个"服务已经停了、设备还在动"的故障。 所有外部观察（systemctl status、进程列表、端口）都会告诉你"已停止"， 只有现场那个还在转的扇叶说明没有。 凡是靠"进程活着"来维持安全状态的系统，都要专门测一次"进程被杀死"。 这类测试不做，等于默认自己永远不会被 kill。

三、没有终端的时候，怎么下指令

服务跑起来之后，第一个撞上的问题是：怎么让杆动一下？

手动模式下是敲 ru 回车。但服务模式下有两个硬约束：

  • 进程的 stdin 不是终端，敲什么都没人读；
  • 14540 端口被这个进程独占了，再起一个实例去连飞控是不可能的。

这逼出了一个很土但非常好用的方案：用文件传话。 

# 写入一行
echo "ru" > ~/px4fan/ctl

# 服务主循环每 50ms 看一次，读到就删掉
[板子] 已下发：ru   ✓ 服务已接收

为什么是"读完即删"而不是"存着读"：保证一条指令只被执行一次。 如果文件留着，主循环每 50ms 就会重复执行一次，杆会被这条指令"钉住"。 删掉之后，语义就变成了一次性的"递条子"。

这个通道能用的命令和手动模式完全一样：

内容效果
35风扇 35%
+5 / -5在当前值上微调
s停
u1250风扇直接给 1250us
c1200 / c0改限速 / 取消限速
ru / rm / rd杆 上 / 停 / 下
r1500杆直接给脉宽

然后给三个最常用的动作各包了一层命令，装到 /usr/local/bin， 这样在任何目录下都能直接敲： 

rod up        杆向上
rod down      杆向下
rod stop      杆停
rod 1600      杆给任意脉宽
rod status    看服务状态 + 最近日志

fan 35        风扇 35%
fan stop      风扇停
fan cap 1200  临时改限速
fan status    看状态

这三个脚本做的事只有一件：往 ctl 写一行字，然后等 1 秒确认服务取走了。 它们不连飞控、不碰端口，所以可以和正在跑的服务共存。 这是设计上刻意的选择：控制通道和数据通道分开，互不影响。

✓
"读完即删 + 等 1 秒确认"解决了最烦的一类问题：指令到底有没有送到。 如果 1 秒内没被取走，脚本会打印 ⚠ 1 秒内没被取走—— 这句话基本等于"服务没在跑"。把"没反应"变成"明确的一条报错"， 现场排查成本差十倍。

四、八个"不报错但没生效"的坑

这一路踩的坑不少，但真正耗时间的不是"报错的"，是那些看起来正常、实际没生效的。 它们的共同点是：所有能被检查的中间环节都显示成功。

#现象以为的原因实际原因怎么一次确认
1 遥控器通道一帧都读不到 接收机没连上 REQUEST_DATA_STREAM 在 PX4 1.16 已废弃，调用不报错、什么都不发 改用 SET_MESSAGE_INTERVAL 订阅，并每 3 秒重发
2 改了 PWM_AUX_FUNC2，杆还是只能遥控器控 参数没保存成功 参数写进 flash 了，但 PWM 只在启动时读一次 重启飞控，再用 probe 看 AUX2 是不是 Set2
3 systemctl stop 之后风扇还在转 服务没停 SIGTERM 让进程直接退出，finally 没执行 信号只置标志位，由主循环走正常退出路径
4 新脚本的功能一个都不生效，unrecognized arguments 代码写错了 scp 没传上去，板子上还是旧文件 sha256sum + 字节数，两个都对再测
5 scp 一直超时 板子网络有问题 IP 给成了 10.41.10.1（eth0 接飞控的口），不是 wlan0 的地址 SSH 用的哪个地址，scp 就用同一个
6 参数改了，服务重启后行为没变 代码有缓存 参数文件不是服务实际读的那一份 启动日志里把生效参数打印出来，对着看
7 键盘方向改对了，遥控器反而反了 遥控器需要重新校准 两个输入源原始方向本来就不同，用了一个全局镜像开关同时翻转 只改出错的那一侧；不要引入"全局开关"
8 示波器上看不到输出 飞控没输出 探针接地没接、或者量的是没被激活的空闲口 先量一个确定在动的口做对照

八条里，属于"代码逻辑写错"的只有第 3 条和第 7 条。 其余六条全部集中在三个地方：文件有没有真的传过去、参数有没有真的被读、订阅有没有真的生效。

这三件事有一个共同点——它们都不报错。 第 4 条最典型：命令输出了 100%，终端没有任何异常， 但文件根本没落到目标目录。这种情况只能靠传完之后核对哈希， 不能靠"看起来成功了"。

!
凡是"我改了但它没变"，一律先证明"改的东西真的到位了"。 顺序是：文件在不在（哈希）→ 参数读没读（启动日志）→ 生效没生效（probe / 示波器）。 跳过前两步直接改代码，是最常见的浪费。

五、验收：拔电，等一分钟，什么都不敲

"开机自启"这件事只有一种验收方式：断电重启，然后不敲任何命令。

步骤做什么应该看到
1 sudo reboot，等一分钟 SSH 能重新连上
2 systemctl is-active px4fan active（不需要手动 start）
3 tail -n 40 ~/px4fan/logs/arbiter.log 出现 已连上 sysid=1、AUX2 绑 Offboard Actuator Set 2、 AUX3 绑 Offboard Actuator Set 3
4 看现场 风扇不转、杆停在中位（两个都是安全初始值）
5 rod up ✓ 服务已接收，杆向上

第 4 步是很多人会忽略的一条：开机自启的目标不是"程序跑起来了"， 而是"跑起来之后设备处于安全状态"。 如果上电瞬间杆就往一个方向走，那这个服务还不如不装。

六、软件兜不住的那一小块

这套东西做到了"程序活着的时候一切都受控"。但它兜不住一种情况：

板子彻底死机。不是进程崩（那会被 Restart=always 拉起来）， 是整个系统卡死——这时候没有任何软件在跑， 飞控收到的最后一条指令永远停在那里，杆会一直顶在限位上， 风扇会一直按最后的转速转，直到有人去拔电。

所以硬件兜底是必须的，具体两件：

  • 两端各一只常闭型微动限位开关，机械到位就断开；
  • 一个继电器模块，串在杆电机的电源正极上， 由限位开关控制。断开电源是真断电，不依赖任何软件。

注意这里是常闭而不是常开：常闭的意思是"没触发就通路"， 线路断了、开关坏了，表现是"杆不动"，而不是"杆失控"。 失效方向要指向安全的一侧，这是硬件兜底的全部意义。

七、四篇连起来

  1. 定结构——飞控做唯一 PWM 输出者，换来一整套现成的失效语义。
  2. 说清协议——归一化、NaN、量化、订阅式接口。
  3. 定语义——松手即停、夺权即作废、超时防堵转、限速截在最后一步。
  4. 变成设备——服务、参数文件、文件通道、快捷命令、断电重启验收。

回头看这半个月，真正难的不是哪一段代码。 难的是每一次"它到底在按谁的规则动"这个问题，都得有一个能一句话说完的答案。 三个被推翻的设计、八个不报错的坑，本质上都在回答同一件事。

如果这个系列只留一句话，我留这句： 让会动的东西，在任何一种失败情况下都只有一个可预期的行为。 做不到这一条，功能再多也不敢让它靠近光伏板。

八、还没做的

  • 没飞过。 所有验证都是吊装地面状态。振动、气流、供电波动完全是另一套输入。
  • 杆的行程没量准。 --rod-timeout 现在按 12 秒给， 真实全行程秒数还没掐表测过——这个数是唯一的依据。
  • 硬件兜底没装。 限位开关和继电器还是纸上的方案。
  • 没有和飞行状态联动。 现在的逻辑不知道飞机是在飞还是在地上， 真正作业时"离板面多近才允许开风机"这类判断还没进去。
