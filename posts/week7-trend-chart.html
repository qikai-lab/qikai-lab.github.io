第 7 周：历史曲线，以及被推翻两次的「串口丢帧」

2026-10-30 · 已通过 SQLite canvas Linux C 排障复盘

这一步原本只想做一件很朴素的事：在网页上加一块「历史趋势」，能切 1 小时和 24 小时。 前面那些图只画最近 60 条原始帧（约 2 分钟），能看出抖动，看不出走势。

做完之后发现，真正花时间的不是画图，是三个「看起来能用、其实是假的」的设计陷阱， 以及一次把自己前两天的结论整个推翻的排查。 前半段讲曲线怎么做，后半段讲那个翻案。

服务端改动在 code/linux_gateway/： 聚合查询在 gw_db.c 的 gw_db_trend()， 接口在 http_srv.c 的 /api/trend， 前端在 web/index.html。

一、24 小时不能查 86400 条，得先压成 96 个点

第一反应是「加个时间范围参数，把这段时间的原始数据全查出来丢给前端」。 算一下就知道不行：24 小时按 1 帧/秒算就是 86400 条，一条 JSON 约 110 字节， 响应体将近 10MB，而网关的响应缓冲区只有 16KB。

正确做法是在 SQL 里按时间分桶聚合，让返回的点数固定， 不随窗口长度增长：

范围桶宽点数看点
1 小时30 秒120 点抖动、掉线缺口
6 小时180 秒120 点半天内的起伏
24 小时900 秒96 点昼夜温差

核心就一句 SQL：

/* 桶起点按整数除法对齐，同一个桶里的数据自然聚到一起 */
SELECT (ts / ?1) * ?1            AS b,
       COUNT(*)                  AS n,
       AVG(temp_x10), MIN(temp_x10), MAX(temp_x10),
       AVG(hum_x10),
       AVG(lux), AVG(gas), MAX(gas),
       SUM(pir)
  FROM env_data
 WHERE ts >= ?2 AND ts <= ?3 AND (node = ?4 OR ?4 = 0)
 GROUP BY b
 ORDER BY b ASC

三个字段是刻意留的，不是凑数：

  • bucket（桶宽）—— 前端靠它判断「相邻两点间隔多少算正常」；
  • n（这桶里有几帧）—— 掉线体检指标，30 秒桶正常 30 帧，掉到 5 就说明那半分钟串口几乎没数据；
  • gmax（桶内最高烟雾）—— 烟雾必须看峰值。烧一张纸只持续 3 秒，在 15 分钟桶里平均下来几乎不变，但峰值会从 23 跳到 300 以上。
!
AVG 要四舍五入，不能直接强转。 温度是 ×10 定点存的，(int)avg 会把 20.45 截成 20.4， 系统性偏低 0.05 度，一百个桶看下来就是一条整体下移的曲线。 加 +0.5 再转，单元测试里专门有一项校验这件事。

二、中间没数据就少一个桶，绝不补 0

查出来「某些桶没有数据」的时候，第一反应通常是补 0 把曲线拉满。 这是个陷阱：补 0 会在曲线上画出一个「温度 0 度 / 光照 0」的深坑， 看图的人以为设备坏了，真相只是那几分钟没有数据。

所以 gw_db_trend() 只返回有数据的桶。 缺口不靠数值表达，靠两个桶之间的时间差表达。 测试用例专门造了一段 300 秒的空白： 

/* 600 秒里只有 300 秒有数据 —— 期望 10 个桶，而不是 20 个 */
n = gw_db_trend(db, T0, T0 + 599, 30, 0, rows, 128);
CHECK(n == 10, "600 秒里只有 300 秒有数据 → 10 个桶（不是 20）");
CHECK(zero == 0, "没有 n=0 的空桶（补 0 会画出假的 0 度）");
CHECK(maxgap == 300, "最大桶间距 300 秒 —— 前端据此断线");

三、X 轴按真实时间定位，不按数组下标

这是整件事里最不显眼、但影响最大的一条。 如果按下标画（第 i 个点放在 i / (n-1) 的位置）， 掉线 5 分钟和掉线 5 秒看起来一样宽——曲线会「假装很连续」。

而这套系统最该暴露的恰好就是掉线。所以改成按时间戳定位： X 坐标由 (ts - t0) / (t1 - t0) 算出来，同时加一条规则—— 相邻两点间隔超过 2.5 倍桶宽，就把线断开（moveTo 而不是 lineTo）。 

/* 断线而不是拉一条斜线糊过去 */
var gapLimit = bucket * 2.5;
for (var i = 0; i < pts.length; i++) {
  var x = pad.l + iw * (pts[i].t - t0) / (t1 - t0);
  var y = ...;
  if (i === 0 || pts[i].t - pts[i-1].t > gapLimit) g.moveTo(x, y);
  else                                                  g.lineTo(x, y);
}

四、16KB 缓冲区装不下坐标轴

网页 HTML 是直接 memcpy 进响应缓冲区再发的， 上限写死在 HTTP_RESP_MAX。加功能之前它是 16384， 而网页已经占掉 14739——只剩 1645 字节，连画坐标轴刻度和悬停气泡的脚本都放不下。

最后提到 32768：网页长到 23784，1 小时趋势接口的响应体实测 13049 字节， 都放得下。代价是每个客户端槽位一份 resp[]，6 个槽位 × 32KB ≈ 192KB。 在 Ubuntu 上毫无压力，但这个设计不可移植到小 MCU—— 真要上单片机，得改成「边生成边发」，不能一口气堆在静态缓冲里。

五、翻案：那个「串口只有 0.33 帧/秒」是假的

前面几周一直有个悬着的问题：串口那条链路测出来只有 0.33 帧/秒， 而同期走 WiFi 的 MQTT 链路是 0.78~1.04 帧/秒。 同样的协调器、同一批帧，一条少三分之二，另一条正常。

按顺序排查，前三次都排错了方向：

#假设怎么验的结果
1 网关程序读得太慢，漏掉了字节 写了个 serial_probe.py 绕开 gw，独占打开串口直接数字节 仍然只有 54%。推翻
2 ESP32 挂在同一个 USB 口上抢带宽 A/B 对照：拔掉 ESP32 再测 拔掉后反而更低（0.20 vs 0.35）。推翻
3 CH340 芯片物理掉线 dmesg 确实有：usb_submit_urb failed: -19、failed to read modem status: -71、converter now disconnected，20 分钟 6 次

到第 3 步，结论看起来已经很扎实了：CH340 在反复从 USB 总线上掉下去， 每次 1.5~1.8 秒，掉的时候数据就丢了。当时的计划是换线、换口。

但有个细节对不上：掉线只占 20 分钟里的 10 秒，撑死影响 1% 的数据， 怎么可能让帧率变成三分之一？

转折出现在一次很普通的启动失败上。手动跑 ./gw，横幅打出： 

 网页   : [启动失败] 端口 8080 可能被占用，采集继续
[db] 入库失败：insert: database is locked（后续失败不再逐条打印）
---- 有效帧=0  坏帧=0  残帧=0  重同步=0B  入库=0  库错=3 ----
---- 有效帧=2  坏帧=0  残帧=0  重同步=0B  入库=0  库错=5 ----

库错 每进来一帧就涨一次，说明有另一个进程拿着 gw.db 的写锁。 可是 ps -ef | grep gw 是空的。

那就查文件句柄，不查进程名：

# 谁开着数据库 —— 这条最准
$ sudo fuser -v gw.db gw.db-wal gw.db-shm
                     USER        PID ACCESS COMMAND
/home/peng/linux_gateway/gw.db:
                     peng       4083 F.... gw

# 抓到 PID 之后，看它归谁管
$ cat /proc/4083/cgroup
1:name=systemd:/system.slice/zigbee-gw.service
                    ↑ 到这里就结束了

有个 systemd 服务在后台跑着第二个 gw。 而且它写的是 Restart=always + RestartSec=3—— 杀掉 3 秒后自动复活，所以你每次 kill 都只是给它换了个 PID： 15:01 是 888，16:44 是 4083，16:50 是 4124，都是同一个东西。

真相到这里就完整了：两个进程在读同一个 /dev/ttyUSB0。 tty 的字节流是被所有读者竞争的，每个进程随机拿到一部分—— 一块可能是完整帧，也可能是半帧。 两边都只能拼出三分之一的完整帧，所以每条链路看起来都「漏了三分之二」。 MQTT 那条不经过串口，自然不受影响。

停掉服务、只留一个进程之后，同一套硬件，实测：

16:55:38  #1   n1  20.6C  42.0%  lux=531(52%)  gas=23  PIR=无人
16:55:39  #2   n1  20.6C  42.0%  lux=531(52%)  gas=23  PIR=无人
...
16:55:59  #21  n1  20.5C  42.0%  lux=532(52%)  gas=23  PIR=无人
---- 有效帧=21  坏帧=0  残帧=0  重同步=11B  入库=21  库错=0 ----

21 秒 21 帧 = 1.000 帧/秒，坏帧 0

1.000 帧/秒。之前那个 0.33 不是硬件问题，不是程序问题， 是有个看不见的第二实例在分食字节流。

→
教训不是「要记得关服务」，而是「先数进程，再改代码」。 前面两天所有关于串口、USB 线、供电、ESP32 干扰的假设， 在「到底有几个 gw 在跑」这个问题面前都不成立。 而这个信息 ps 给不出来——因为服务进程的名字就叫 gw， 父进程是 PID 1，看起来像一个正常常驻进程。 真正给出答案的是 /proc/<pid>/cgroup 里那行 .service。

顺带修正了另一样东西：dmesg 里那些 -19 / -71 是真的， CH340 确实在偶发掉线。但它只是次要因素，不是三倍差距的原因。 把次要原因当成主因，是这个项目里代价最大的一次误判。

六、验收：230 项断言 + 浏览器里逐项看过

服务端加了一组 tests/test_trend.c，32 项断言，覆盖分桶边界、 四舍五入、断档不补 0、峰值不被平均抹平、节点过滤、24 小时 96 桶、参数防御。 全套离线测试现在是 230 项，不需要串口、不需要板子。

前端没法写单元测试，所以做了个假网关 tools/mock_gw.py， 在本地起一个只返回假数据的服务，用真实浏览器打开看：

七、诚实说明：24 小时视图现在画不满

库里现有的 4000 多条数据是这几天间歇采集攒下来的，中间有大段空白 （机器不是一直开着，传感器也不能连着跑一整天）。 所以 24 小时视图现在是一条断续的线，不是满格。

这不是 bug，恰恰是「断档不补 0」在起作用—— 系统不会用一条直线把没有数据的时间糊过去，它会把缺口如实画出来。 等哪天连续跑满一天，它自然就是连续的一条。

八、还剩什么

  1. 低功耗与电池续航实测——需要万用表量电流、拆掉 USB 供电， 当前硬件条件不够，暂时挂起。这一项不影响主链路。
  2. 长时间稳定性——需要连续跑 24 小时以上。 同样受硬件条件限制，放到最后。
  3. 趋势图的视觉细节——光照（左轴 38~64）和烟雾（右轴 4~30） 在数值接近时两条线会贴在一起，看起来像少画了一条。 数据巧合，改量程或加虚线都能解决，优先级不高。
→
到这一步，主链路是完整闭环了。 采集 → 组网 → 落库 → 网页 → 告警 → 上云 → 远控 → 历史趋势。 从一块 CC2530 到 Linux 上跑着的 C 服务端，每一段都自己写过、断过、修过。 剩下的都是「有条件才做」的加分项，不影响这套系统能不能跑。
